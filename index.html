Agent work, in order.

Sortyard is a delivery harness for software built by AI agents: the conductor, the control plane and the task manager, in one package you run on your own cluster. It is the harness we use, rebuilt from first principles.

Why it exists

It started as an audit. We checked the system we use to build software with agents against its own records. The harness turned out to be spread across about six repositories, with two schedulers making decisions, and many of its operating rules lived in documents and in an agent's memory instead of in the system itself.

Sortyard is the redesign: the same control and flexibility, packaged so anyone can install it. We run it ourselves first and replace our current harness by cutover, starting with Sortyard's own backlog.

Principles

No unbound agents

Work runs only through a verified binding: workflow, context, skills, model, place, credentials and a bounded resource envelope.

One source of truth

Each domain object has one home. Everything else is a labelled projection of it.

An explicit state machine

Item states are data. The conductor's next step can be derived from them, not guessed.

Observed state only

Work advances on what the system observes, never on an agent's report of what it did.

Where it stands

  1. Charter and full design spec published before any product code
  2. Phase 1: API service, Postgres domain schema and event ledger, one Helm chart, and a local replica on kind
  3. Kernel work under way: a durable workflow engine, item states as one table, and a ledger that records every transition
  4. Next: run one delivery lane end to end, then cut over our own harness

Try it

You need Docker, kind, kubectl and Helm 3. From a clone of the repository:

./replica/replica.sh up

This brings up an empty Sortyard on a local cluster and smoke-tests it. ./replica/replica.sh down removes it.
